## 1. S5a: vSphere networks on reservations, power and locking: integrated

S5a is mblanke/TrueNorth#33, by its own session. It moves the vmware branch's VLAN and
uplink allocation onto `network_reservations`: worker-side, same advisory lock as the API,
no Redis, no unlocked fallback. It also makes start/stop fenced range operations. Its
evidence (before 37/49 failing, after 71 passing, a Postgres race that handed out duplicate
VLANs with Redis down, now never) is in `docs/hardening/evidence/s5a-*.txt` on its branch.

It is now merged into the candidate (merge `b23a787`). That needed one design decision:
#33 and #30 both turned `/stop` into an operation, with the same new states and the same
migration id. **#33's design is kept**, because it runs on the vmware provisioner and its
state-machine change was approved by the owner:

- a start ends in `running`;
- a failed power operation leaves the range `failed`, from where it can be started or
  stopped again;
- provisioning over recorded VMs is refused ("destroy it first"), so nothing is orphaned.

These parts of #30 are kept on top of it:

- operations wait for a restore in progress;
- a restore settles finished operations first;
- an exercise does not run on a powered-off range;
- the failed-operation text in the range list;
- the worker import-order fix (`worker/reliable.py`, which now also carries
  `PermanentError`);
- vSphere power also accepting `ALREADY_IN_DESIRED_STATE` between its state check and the
  call. That case fails first on #33's file, in 2 tests.

**Merge order for a human:** merge #33 before #30. #30's power code is then superseded:
resolve it as #24 does (take #33's side; keep the items above). Whichever of #29/#33
merges second rechains its migration (#24: `d1e2f3a4b5c6` after `a9b0c1d2e3f4`).

**Known gap from the merge:** the noise engine's management NIC (#29) was written for
main's REST provisioner, which #33 replaced. The noise API side (reserved addresses) is
unaffected. The vSphere NIC is not there yet, so `tests/worker/test_vsphere_noise.py` is
skipped, with the reason in the file. The port renders the noise NIC into `nics` on the
shared noise port group.

## 2. Lab run against vCenter: ready to run, needs your credentials

vCenter is up again after the restart. It answers HTTPS at `192.168.1.10`, and its API
returns 401 without credentials. This session has no vCenter credentials and is not
allowed to type passwords, so it cannot log in for you.

`scripts/lab/candidate_smoke.py` runs runbook §5's smoke test on a checkout of the
candidate. It is plan-only unless you add `--apply`. With `--apply` it uses a scratch
database, a throwaway Redis, this checkout's API and a real worker with the `vsphere_api`
backend. It runs:

1. provision a one-VM Ubuntu range;
2. record its VLAN/uplink reservations;
3. stop → `stopped`;
4. start → `running`;
5. destroy, and check that its reservations were released.

With `--concurrent` it also provisions two ranges at once and checks that their VLANs are
disjoint. Whatever happens, it destroys anything it built. It writes the steps to
`docs/hardening/evidence/lab-smoke-<time>.json`, with no credentials.

From a checkout of `hardening/integration-candidate`, in your own terminal:

```bash
export VSPHERE_URL=https://192.168.1.10 VSPHERE_USERNAME=svc-truenorth@vsphere.local
export VSPHERE_DATACENTER=<dc> VSPHERE_CLUSTER=<cluster>
read -rs VSPHERE_PASSWORD && export VSPHERE_PASSWORD
export TEST_POSTGRES_ADMIN_URL=postgresql+psycopg://<user>:<pass>@127.0.0.1:5433/postgres
.venv/bin/python scripts/lab/candidate_smoke.py
.venv/bin/python scripts/lab/candidate_smoke.py --apply --concurrent
```

Prerequisites (runbook §4.2 and §5.1):
- the `TrueNorth-Provision` role on `svc-truenorth`;
- the template `tmpl-ubuntu-2404`. Set `LAB_TEMPLATE` if yours has another name.

A 403 names the missing privilege. Commit the evidence file; that closes the lab check in
S8.

## 3. Course Studio runner account: needs you

This was not done here, by rule rather than by choice: the session may not create accounts
or handle passwords. Creating a macOS user needs an administrator password, and
`claude setup-token` is an interactive sign-in. The steps are in
[`docs/arc2-course-studio.md`](../arc2-course-studio.md), under "Runner
account":

1. **System Settings → Users & Groups:** add a standard user `arc2runner`. It must not be
   an administrator or in the `docker` group.
2. **As `arc2runner`:**
   - clone the repo;
   - `uv venv .venv --python 3.11 && uv pip install -r requirements-test.txt`;
   - install Claude Code;
   - run `claude setup-token`;
   - save the token to `~/.arc2/oauth-token` (`chmod 600`).
3. **The runs folder:** give `arc2runner` write access to `build/arc2`, and the API read
   access.
4. **Start the runner:** `make arc2-runner` as that user. It prints `confinement:
   seatbelt`.

Then a Studio run with the real engine completes the "Studio journey" check (S8
Integration).
