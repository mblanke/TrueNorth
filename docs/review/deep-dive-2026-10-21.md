## Actionable findings

### D21-01 — P1: QSP reads expose another tenant's curriculum and course metadata

**Confirmed in three additional API probes.** As a Student in tenant A, listing qualifications includes a qualification owned by B; requesting B's objectives returns 200 rather than 404. More importantly, a globally shared qualification with an objective delivered by B's private course exposes that course's ID, name, module ID and module title to A through `delivered_by`.

The first two cases are already tracked in [issue #227](https://github.com/mblanke/TrueNorth/issues/227). The shared-objective case means filtering only the qualification rows is insufficient: a legitimate shared qualification still reaches unfiltered tenant-owned descendants.

Source: [qualification endpoints](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/api/app/routers/qsp.py#L399), [module lookup](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/api/app/routers/qsp.py#L178), and [PO context](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/api/app/routers/qsp.py#L435).

**Correction:** pass caller visibility through the qualification, objective, course/module, lesson and exercise-reference queries. Own-tenant and explicitly shared content must remain readable; foreign private records must not appear. Audit curriculum-map consumers of the same helpers. Preserve the three failing probes as regressions and add equivalent coverage for related references. Treat this as a release blocker for multi-tenant use, not a later classroom convenience.

### D21-02 — P2: guest-IP readiness deadlines depend on vCenter remaining reachable

**Confirmed in an additional worker probe.** A build can exhaust its own budget, leave a VM's `ip_check` running, and return a ready range pending reconciliation. If vCenter or its connection then becomes unavailable, `_get_backend` or `reconcile_guest_ips` raises. `_reconcile_range` logs the error and returns without recording an expired IP deadline. Repeated outages can therefore leave an already-expired check running indefinitely.

The existing product/Security Onion setup timeout path settles deadlines from stored records before connecting; IP checks do not share that protection. Existing tests cover successful backend verdicts and setup timeouts, but not an expired IP check with an unavailable backend.

Source: [setup reconciliation, lines 232–247](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/worker/worker/setup_reconcile.py#L232), [backend readiness read](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/worker/worker/provisioners/vsphere_api.py#L2409).

**Correction:** settle expired IP checks even when remote reads fail, with an explicit unverified/unavailable outcome rather than falsely claiming a guest-network failure. Apply the existing state guards so reconciliation cannot overwrite an operator action. Test unreachable vCenter, removed connection, refused ownership screening and successful verification before expiry.

### D21-03 — P2: host-local template naming is inconsistent for IP-address hosts

**Confirmed in an additional pure-function probe and source trace.** For host `10.20.30.40`, Python produces `ubuntu@10.20.30.40-20261021`, but the parser rejects dots in the host component. The replication shell script instead truncates the host to `10`. Neither name resolves through `newest_on_host` for the full IP. Replication may also fail host lookup or target-name selection before a copy exists.

This can bypass the intended host-local clone optimization, or fail builds relying on those copies. The module matrix already described this as an estimated risk; this review reproduces the naming failure, without claiming it has occurred on the work vCenter.

Source: [copy naming/parser](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/control-plane/worker/worker/provisioners/template_copies.py#L18), [replication naming](https://github.com/mblanke/TrueNorth/blob/d4b3689cfe758dcc87ce24932d3b58c864df84dd/infra/vsphere/packer/build.sh#L226).

**Correction:** define one collision-safe host identifier and use it in replication, discovery, lookup and pruning. Test FQDNs, IP addresses, case normalization and hosts sharing the same first label/octet. Account for existing copy names before changing conventions.

## Known limitations and release controls still open

- **Historical participation is mutable.** The existing test `test_r3_known_limitation_reopening_after_a_sat_run_drops_its_roster_seat` passes by asserting that a learner loses a previous run's AAR access after withdrawal and re-enrolment, unless a team or detection separately establishes participation. This is deliberately documented, not a newly discovered regression. [Issue #224](https://github.com/mblanke/TrueNorth/issues/224) needs seat-period history or immutable run participation. The unified learning record should not build historical claims from only the current enrolment period.
- **Browser journeys are not a required merge check.** Live branch-protection settings contain `e2e`, but omit the separate `journeys` check. The current `journeys` run passes; future failures would not be blocked by that required-check list. [Issue #197](https://github.com/mblanke/TrueNorth/issues/197) remains open. Also audit new critical lanes against the required list; job existence and merge enforcement are distinct.
- **Chained firewalls remain unsupported.** [Issue #235](https://github.com/mblanke/TrueNorth/issues/235) explains the missing transit/static-route model. Red vs Blue's secondary firewalls are not on the intended traffic path; Large Enterprise's OT enclave remains isolated. The templates document these compromises. Do not represent them as a completed multi-tier network defence scenario.
- **Site evidence is still outstanding.** [#191](https://github.com/mblanke/TrueNorth/issues/191), [#202](https://github.com/mblanke/TrueNorth/issues/202) and [#210](https://github.com/mblanke/TrueNorth/issues/210) remain open for installation, strict acceptance and real range proof. Their rc11 wording now needs reconciliation with rc12 and newer main. The matrix says staging was offline for the rc11 record; that historical observation is not a current host probe.
- **Student range password rotation remains deferred** in [#198](https://github.com/mblanke/TrueNorth/issues/198). Define cohort/reset boundaries before relying on reusable range credentials for successive classes.
- **Documentation is inconsistent.** The matrix now includes rc11 evidence and the October 20 amendment, while `docs/current-state.md` still names rc3 and the release notes still have a blank final staging record and obsolete MFA wording. The changelog's broad staging claim is not a substitute for candidate-specific evidence.
