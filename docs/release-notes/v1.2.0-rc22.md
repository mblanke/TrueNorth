# v1.2.0-rc22: upgrade notes (from rc21)

What a site upgrading from `v1.2.0-rc21` to `v1.2.0-rc22` needs to know. How to upgrade is
guide 06 §2 ([`06-operations-runbook.md`](../guides/06-operations-runbook.md)). The previous
notes are [`v1.2.0-rc21.md`](v1.2.0-rc21.md); known limitations are in [`v1.2.0.md`](v1.2.0.md).

**Unlike rc21, rc22 is not an image bump only.** It adds two database migrations and a
setting, and brings in the support and wiki features. Read this before the window.

## Database: two additive migrations

Both create a new table and write no rows; the upgrade's pre-upgrade backup
(`tn_pre_upgrade_backup`, on by default) still runs first.

| Revision | Table | What for |
|---|---|---|
| `b4d6f8a0c2e4` | `notification_preferences` | A user's own on/off for emailed ticket notifications (no row means on) |
| `c5e7a9b1d3f4` | `wiki_images` | Metadata for images uploaded to wiki pages (the bytes stay in object storage) |

Downgrading drops those tables. The installer refuses to go backwards (a database newer than
the code) unless told to; if you roll back to rc21, follow guide 06 §2.4 and prefer the
pre-upgrade backup to a downgrade. Not rehearsed: a rc22 to rc21 rollback.

## Settings

One new installer setting, `tn_class_observer_consoles` (default `false`; preflight refuses
anything but `true` or `false`). `false` keeps observers on live status only; `true` lets
observers on a class open its Students' consoles, read-only (ADR 0014 §19). The default
matches the owner decision, so an upgrade changes nothing until you set it. No new required
vault key.

## What is new

- **Support and wiki** (issues #376 to #381): ticket category and label screening, push
  notifications to the bell, ticket email with no ticket text in it, images in wiki pages
  (visible only to whoever can see the page), search ranked through OpenSearch with the
  database deciding who sees what, and AI triage suggestions for staff, **opt-in** and
  suggest-only. The last-mile plan had deferred these to v1.2.1; they are merged on main, so
  rc22 includes them. They have had review and CI but no site use: treat them as first-release code.
- **Exercise credit** (#375): results credit the exercise's Students, never the instructor,
  and a collective exercise on a shared class range credits the class roll call when no team
  is set. See guide 04.
- **Installer:** `--check` works on a fresh host (the release tasks that must really run no
  longer simulate), the first sign-in is the break-glass account, and a site without vCenter
  can install with `tn_provisioner_backend: mock` (guides: Phase A of the clean-room
  protocol).
- **Release:** the signed release carries the guide PDFs (best-effort; a release can lack
  them if that job failed).
- **Content:** 13 courses now name every lab host in the step that uses it; per-template
  lab checklists are in `docs/lab-checks/`.
- **Web:** the duplicate exercise-template routes are registered once.
- **Source files** carry an authorship header (`Author`, `Created`): no behaviour change.

## Behaviour that did not change

The #443 fixes of rc21 stand; the rest of that audit's findings (#443, #493) are still open.
No other default changed.
