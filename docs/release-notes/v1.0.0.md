# TrueNorth Range v1.0.0: known limitations and staging record

What changed is in [`CHANGELOG.md`](../../CHANGELOG.md) (v1.0.0, its upgrade notes and
the release candidates). How a release is built, signed and verified is in
[`docs/release.md`](../release.md). This page covers two things the changelog only
summarises: what does not work yet, and what was verified on the staging host.

Written 2026-10-09 against `v1.0.0-rc3` (`e015d27`).

## Known limitations in v1.0.0

Each item below was checked against the code at `v1.0.0-rc3`.

### LTI deep linking for staff whose email matches

`_jit_user` in `control-plane/api/app/routers/integrations.py` runs for every LTI
launch, deep-linking requests included. The LMS asserts the email claim and TrueNorth
does not verify it, so an email links an existing account only when that account is a
Student in the platform's own tenant. If the email belongs to an instructor or admin
in that tenant, the launch gets a 403 ("Staff accounts are not signed in through the
learning platform"). As a result, an instructor whose LMS email is also their
TrueNorth email cannot use deep linking (the content picker) from the LMS.

**Workaround:** none in v1.0.0 that keeps the protection. Do not demote staff accounts
to Student to get around it.

### Student telemetry search on range indices from before the upgrade

Since #112 (H4, ADR 0005) the scenario engine writes inject labels under
`tn_ground_truth`, and the `range-*` template maps that field `enabled: false`, so it
is never indexed. A range index created before the upgrade does not have this mapping:
it still has the old flat labels, or it maps `tn_ground_truth` dynamically. The search
endpoint (`GET /telemetry/{range_id}/search`, in `control-plane/api/app/main.py`) gives
non-staff callers a 422 for label field terms and strips labels from each hit. However,
a free-text term still matches indexed label values on such an index, so a Student can
find out which events were injects.

Fresh installs are not affected.

**Workaround on an upgraded site:**
1. Re-run the telemetry bootstrap so the index templates are current:
   `install/playbooks/70-telemetry.yml`, which runs
   `python -m telemetry.pipelines.bootstrap` in the api image. The bootstrap PUTs every
   index template.
2. Recreate (or reindex into a fresh index) every `range-*` index created before the
   upgrade that a Student can still reach.

### Per-tenant hypervisor credentials are not used by `vsphere_api` (H6)

The H6 fix (#112) makes the worker resolve the range's own tenant's
`HypervisorConnection` (`worker/db_ops.hypervisor_creds`) and pass it to the
provisioner as `template["credentials"]`. The `vsphere_api` backend is built through
`get_provisioner(name)` with no credentials and does not read
`template["credentials"]`. It always uses the worker's `VSPHERE_*` environment, so
the install has a single vCenter. The fix stops one tenant's connection from being
used for another tenant's range. It does **not** give each tenant its own vCenter.

### Multi-tenant installs must set `PLATFORM_TENANT_ID`

Admins are per tenant. If `PLATFORM_TENANT_ID` is unset and more than one tenant
exists, nobody is the platform administrator. Creating tenants, cross-tenant approval
and platform-wide settings are then refused, and the API logs why at startup
(`control-plane/api/app/rbac.py`). Single-tenant installs are unaffected. Set it to
the operator's tenant id.

### OpenSearch telemetry is not in backups by default

`scripts/backup/backup.sh` snapshots OpenSearch only when `OPENSEARCH_SNAPSHOT_REPO`
names a registered snapshot repository. Without it, the backup records OpenSearch as
`not-backed-up` and logs a warning. To include telemetry, configure
`OPENSEARCH_SNAPSHOT_REPO` (`docs/operations.md`, backup table).

### LTI needs HTTPS

The LTI launch state cookie is set `Secure; SameSite=None`, because the LMS posts the
launch cross-site. By default the launch is refused unless the browser presents that
cookie, so LTI works only over HTTPS. If the tool runs in an iframe and the browsers
block third-party cookies, set `LTI_REQUIRE_STATE_COOKIE=false`. That turns off the
login-CSRF binding for those launches.

### No live vCenter run yet

The nightly live lab workflow (`.github/workflows/lab.yml`, self-hosted runner,
`docs/runbooks/lab-runner.md`) has not yet run against a real vCenter. So far,
provisioning has been validated only against govmomi's vcsim (the CI `vsphere-sim`
lane). On staging, the hypervisor dashboards read a simulated, read-only vCenter
(`tools/vcenter-sim`), which answers every provisioning call with 403. Range
provisioning against real vSphere is therefore **untested** in v1.0.0. The live run on
TN-MGMT01 is planned for v1.0.1.
