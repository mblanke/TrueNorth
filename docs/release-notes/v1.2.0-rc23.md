# v1.2.0-rc23: upgrade notes (from rc22)

What a site upgrading from `v1.2.0-rc22` to `v1.2.0-rc23` needs to know. How to upgrade is
guide 06 §2 ([`06-operations-runbook.md`](../guides/06-operations-runbook.md)). The previous
notes are [`v1.2.0-rc22.md`](v1.2.0-rc22.md); known limitations are in [`v1.2.0.md`](v1.2.0.md).

**rc23 is not an image bump only.** It adds one database migration that can refuse to run,
the installer takes over two lines of `.env.production`, and Windows range VMs get a
different time zone by default. Read this before the window.

## Database: one migration, and it can refuse

| Revision | Change | What for |
|---|---|---|
| `d6f8b0a2c4e5` | Unique index `uq_imported_result_first_per_attempt` on `imported_results` | At most one first result per attempt from an enclave (audit #443 f34); a correction names the result it replaces and is not counted |

It writes no rows. **It refuses to run if the table already holds two first results of one
attempt**, and names them (`source_enclave`, `attempt_id`, count). Keep one, supersede or
remove the others, and upgrade again. A site that has never imported results from an enclave
has an empty table and is not affected. The pre-upgrade backup (`tn_pre_upgrade_backup`, on
by default) runs first.

Downgrading drops the index. Not rehearsed: a rc23 to rc22 rollback; follow guide 06 §2.4
and prefer the pre-upgrade backup to a downgrade.

## Settings

No new required vault key. Three optional settings:

- `tn_vsphere_so_install_user` (default `soadmin`) and `tn_vsphere_so_install_password`
  (`vault_vsphere_so_install_password`, else `vault_template_linux_password`): Security
  Onion's install login. **The installer now owns `VSPHERE_SO_INSTALL_USER` and
  `VSPHERE_SO_INSTALL_PASSWORD` in `.env.production`.** A site that added those two lines by
  hand (the work site did, on 2026-11-23) sets the same values in its inventory or vault
  before upgrading, or the upgrade replaces them with the defaults. Preflight warns on vSphere
  when either is empty.
- `tn_vsphere_windows_timezone` (`VSPHERE_WINDOWS_TIMEZONE`, a decimal index from
  Microsoft's table; preflight and the worker check it). See the next section.

## Behaviour that changed

- **Windows range VMs are set to Eastern Standard Time (index 35), not GMT (85)**, unless
  `tn_vsphere_windows_timezone` says otherwise (owner decision 2026-11-23, #526). Ranges
  already built keep the zone they have.
- **The CSRF cookie** (`truenorth_csrf`) is issued once and kept, as a session cookie; it was
  replaced on every read, with a one-day lifetime (#537). This fixes writes refused with
  "CSRF token missing or invalid" when a page was still reading. A browser left open across
  the upgrade keeps its old one-day cookie; a write after that lapses is refused once, until
  the page's next read. Scripts that call the API read the cookie before each write, as the
  shipped ones do.
- **Security fixes from the #443 audit** (each refuses something that was allowed):
  - only the platform administrator changes a platform-default auth zone (#516);
  - Forge never binds an exercise to a Student's lab range (#518);
  - `require_tenant_access` checks the path parameter it names (#519);
  - public templates and scenarios are read by id (#521);
  - a Student's telemetry free text never searches the inject labels (#523);
  - one first result per attempt, and a reused `package_id` is a refusal with a reason,
    not a server error (#524);
  - a withdrawn Student cannot launch, read or grade a cmi5 module (#525).

  The state of every finding is in the audit ledger (#515).

## What is new

- **Golden Images page:** promote a build in place, with a required reason; sort and filter
  by status (#527). Guide 03 describes it.
- **Where a range build's time goes:** a vSphere build records seconds per phase and per VM
  in the range's provisioner output (`timings`), with one worker log line naming the slowest
  phases (#536). Read it in `docs/deployment/vmware-site-runbook.md`, "Where a build's time
  goes". No screen shows it yet, and no build has been timed on real hardware.
- **Template kit:** the 2026-11-23 and 11-24 work-site fixes are in the repository (#530,
  #533): pfSense installer hotkeys, the Windows test-clone time zone, Parrot over http with
  apt retries. The pfSense part is proven on site. **The Parrot part is not proven end to
  end.**
- **Depot mirrors for greyspace-host** (Docker apt, Alpine, Docker Hub, quay.io; #534):
  designed, **not proven on site**.

## Not in rc23

The golden images that still fail on the work site (srv2019 and win10-22h2: VMware Tools
never installs in the guest; vyos; the role installers) are not fixed by this release. The
record is `docs/lab-checks/audit-2026-11-23.md`.

## Verify

The installer's migration step (`50-stack-up`) must finish clean; it applies the revision
above. Then strict acceptance S and H (`~/.truenorth-work-acceptance.sh`) and System Health.
On a vSphere site, build one SOC range to confirm the Security Onion install login, and read
`timings` in its provisioner output.
