## Per-module records

Each record lists: the supported workflows (v1.2.0 contract), the mandatory checks, the permitted skips, the environments,
monitoring and backup, and the limitations. "Excluded" items come from plan §7 and are outside the
contract even when an API exists.

### 1. platform-core
- **Supported:** sign-in through Keycloak; users and roles (admin, instructor, range_ops, student, observer); RBAC on every route; tenant scoping; audit log of writes; registration intake and approval; demo accounts linked to Keycloak.
- **Mandatory (S):** `platform-core / users for each role` · `platform-core / RBAC: Student and Observer refused staff routes` · `platform-core / tenant scoping` · `platform-core / audit log records writes` · `platform-core / demo accounts linked to Keycloak` (pass `KEYCLOAK_ADMIN_PASSWORD` to the one-off container, as the runbook does; without it the check skips and `--strict` fails it).
- **Permitted skips:** none on S. CI-I: Keycloak link (`keycloak` absent).
- **Environments:** U, CI-I, S, B.
- **Monitoring:** ApiHighErrorRate, ApiHighLatencyP95, PgConnectionPoolExhaustion. **Backup:** yes (app and keycloak databases in the Postgres dumps; secrets escrowed).
- **Limitations:** instructors cannot reach approvals in the UI (triage d); users import-csv and team membership are API-only (triage g); audit export, retention, login banner and MFA policy are claimed in docs but not built (triage h). AD/LDAP sign-in is M2 and not advertised.

### 2. web-shell
- **Supported:** the Angular shell through nginx; main routes per role; deep links behind guards.
- **Mandatory (S):** `web-shell / SPA served through nginx` · `web-shell / each main route's API, by role`.
- **Permitted skips:** none on S. CI-I: SPA through nginx (`edge` absent).
- **Environments:** U (Karma), CI-I, CI-R (e2e), S, B.
- **Monitoring:** NodeDown (host only). There is no probe for the web container; Docker health only. **Backup:** not applicable (stateless image).
- **Limitations:** menus are not role-aware; no Observer view; range_ops is blocked from Ranges and templates; `/telemetry` has no menu entry; dashboard quick actions lead to routes the role cannot open (triage e); the readiness and development previews (fictional) are visible to every learner (triage f); English only (triage j).

### 3. infra
- **Supported:** health (live, ready, deep); `/metrics` behind its scrape token and refused at the edge; nightly backup; Prometheus rules and Grafana.
- **Mandatory (S):** `infra / health live + ready` · `infra / health deep: every component` · `infra / metrics need the scrape token` · `infra / edge: health, API, metrics refused` · `infra / backup environment present` (mount the host config read-only and pass `--host-config`).
- **Permitted skips:** none on S. CI-I: metrics token, edge, backup.
- **Environments:** U, CI-I, S. Restore drill: isolated target (plan §6).
- **Monitoring:** all host, API, Celery, Postgres, Redis, OpenSearch and backup rules, MoodleDown, Arc2RunnerDown. **Delivery is not proven:** staging's Alertmanager uses `alertmanager.yml`, where every route goes to the `null` receiver (no webhook configured). On 2026-10-12, `ApiHighLatencyP95` had been firing since 2026-10-10T13:14Z (p95 about 7.75 s) and reached no one. **Backup:** this module is the backup; restore is unproven until the drill.
- **Limitations:** the backup does not stop the ARC² runner, so a run in progress may be copied half-written (`scripts/backup/backup.sh:25-26`); OpenSearch is backed up only through its snapshot repository; Redis is not backed up, by design.

### 4. scenario-engine
- **Supported:** a scenario validates and becomes an exercise plan with its objectives and timeline; start; the worker fires timeline injects; pause and resume; complete.
- **Mandatory (S):** `scenario-engine / shipped scenario becomes an exercise plan` · `scenario-engine / start, inject fired by the worker, pause, resume`. Staging is `vsphere_api`, so the mock-backend skip in the lifecycle check must not occur; under `--strict` it would FAIL.
- **Permitted skips:** none.
- **Environments:** U, CI-I, S, B.
- **Monitoring:** CeleryHighTaskFailureRate, CeleryDeadWorkers. **Backup:** yes (exercises, injects and objectives in Postgres).
- **Limitations:** injects are simulated. `email_phish`, `http_burst` and `identity_new_admin_user` report delivery or creation without touching a host, and inject data is unseeded random (triage a). Live host injectors are excluded (plan §7). The UI Resume button is broken (triage b). The `scenario-engine` image is published but not deployed on staging.

### 5. ai-arc2
- **Supported:** the AI orchestrator answers through the API (detection draft); the ARC² Course Studio, with a runner under systemd, generates, QAs and releases courses; on a test host, auto-accepted releases are labelled TEST CONTENT, and anywhere else they are refused.
- **Mandatory (S):** `ai-arc2 / AI orchestrator answers through the API` · `ai-arc2 / ARC² Course Studio enabled`.
- **Permitted skips:** none on S. CI-I: Studio (`arc2` absent).
- **Environments:** U, CI-I, S.
- **Monitoring:** Arc2RunnerDown (`truenorth_probe_up{component="arc2-runner"}`, from the systemd unit state; on 2026-10-12 it read 1). There is no job-level heartbeat or oldest-queued-job metric. **Backup:** ARC² runs are archived (`arc2/runs.tar`); the runner is not quiesced.
- **Production profile:** with `TN_TEST_HOST` unset, the API refuses to accept or publish a release whose gates the runner auto-accepted: `tests/api/test_release_test_content.py::TestAcceptAndLabel::test_off_a_test_host_test_content_is_never_accepted` (409), `TestPublish::test_test_content_accepted_on_a_test_host_does_not_publish_once_the_flag_is_off`, and `test_a_queued_job_fails_rather_than_publish_off_a_test_host`. The installer writes `TN_TEST_HOST=true` only with `tn_arc2_auto_accept` (`install/roles/tn_config/templates/env.production.j2:221-225`; `tests/contracts/test_installer_arc2.py::test_only_an_auto_accepting_host_is_a_test_host_for_the_api`), and compose defaults it to `false`. Staging's api has `TN_TEST_HOST=true`, which is expected for a test host.
- **Limitations:** ARC² Observe and Access are excluded; no PCTE claim; the local-model fallback must record the model actually served (plan, Content and ARC²).

### 6. lms
- **Supported:** course catalogue; enrolment; quizzes and module progress; the PO on the curriculum map; cmi5 AU launch with statements to the LRS; Moodle as the registered platform (reachability, results list, publish).
- **Mandatory (S):** `lms / enrol, sit a quiz, progress recorded` · `lms / cmi5 launch, fetch, statements to the LRS` · `lms / Moodle platform reachable`.
- **Permitted skips:** none on S. CI-I: cmi5 (`lrs` absent) and Moodle (`moodle` absent); covered by the CI `cmi5-conformance` and `moodle` lanes.
- **Environments:** U, CI-I, CI-R (moodle, cmi5-conformance), S, B.
- **Monitoring:** MoodleDown (on 2026-10-12, `truenorth_probe_up{component="moodle"}` read 1). There is no grade-sync lag or pending-publication metric (plan §6). **Backup:** yes (Moodle database, `moodledata.tar`, LRS database).
- **Predicted blocker (estimate, not observed):** staging's api has **no `CMI5_LRS_AUTH`**, and `app/cmi5/lms.py:128-130` fails closed with 503. Once an accepted cmi5 release is on a published course, the cmi5 check would FAIL; before that, it skips with "no accepted course release", and `--strict` fails that as well. In both cases cmi5, which is in scope, cannot pass on staging until the installer mints and sets the credential.
- **Limitations:** no self-enrol UI (triage c); per-learner progress and completion, and Moodle results and pull-now, are API-only (triage g); the multi-tenant Moodle farm loop is excluded; no PCTE hand-off.
